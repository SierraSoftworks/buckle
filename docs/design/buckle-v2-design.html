    Buckle v2: fleet configuration with phased rollouts

    A single Rust binary that runs as a planner, a persistent agent, or a rollout server. Modules declare idempotent tasks, health checks and cleanup; the server watches Git, ships revisions over Tailscale, and orchestrates feedback-controlled rollouts with a human sign-off gate on the plan.

    00

    What v2 is, in one screen

    Buckle v1 is a bootstrapper: it walks a directory of packages, writes files and runs scripts. Buckle v2 keeps that single-binary, zero-ceremony feel and becomes a fleet configuration system: declarative idempotent tasks, continuous agents, a Git-watching server, phased rollouts gated on health and human approval, and a UI to watch it all.

    Lightweight

    One static binary (musl) for agent and server. Agent idles at a few MB RSS: one gRPC stream, one timer, no interpreter. Bootstrapping is buckle install agent --server ….

    Fast

    Modules run as a dependency DAG with parallel execution; tasks declare resource locks (e.g. apt) so unrelated work overlaps. Plan is a pure read phase; apply touches only what changed.

    Observable

    One trace per rollout spanning server and every agent (W3C trace context in gRPC metadata and in the Apply, Rollback and RunHealth messages). Spans per module, task and health check with change counts; OTLP gauges for rollout hosts and connected agents; the UI shows the trace id and links it when a trace URL template is configured.

    Operable at scale

    Phased rollouts with bake time and failure budgets, automatic pause, one-click rollback to the last stable revision, drift detection and correction, and removal cleanup so hosts converge instead of accumulating debris.

    What changes from v1

    v1 is 1,400 lines of Rust: apply and plan commands over a Core with mockable Launcher, FileWriter and Output traits. Keep the spirit (trait-backed core, mockall tests, human-errors, tracing-batteries), replace the execution model.

    Decision

    v2 replaces v1 on main as Buckle 2.0.0. The v1 code is deleted rather than kept as a legacy mode; the migration helper and a documented mapping cover the transition. Keeping two engines in one binary would double the test surface for a tool with a small user base.

    02

    System topology

    One binary, three roles. The server is the only component with state about the fleet; agents hold only their own state. Everything between them crosses the tailnet.

    Processes and roles

    buckle plan / apply

    One-shot against a config directory, same engine as the agent. Used for authoring, CI validation and bootstrap before an agent is installed.

    buckle agent

    Long-running. Connects to a server (or watches a local directory), applies assigned revisions, runs health checks, reports facts and results, re-plans periodically for drift.

    buckle server

    Watches Git, builds revisions, orchestrates rollouts, serves gRPC to agents and the OIDC-protected HTTP API and UI to operators.

    Decision · agreed

    One binary, one build. The release artefact is the full buckle binary with agent, server and embedded UI; there is no slim agent variant. Target size is under 15 MB stripped (musl, LTO, codegen-units = 1, panic = "abort", release-mode Trunk build of the UI, symbols published separately as the reference repos do). CI reports the binary size per platform; a feature flag to drop the server from the agent build is reconsidered only if the full binary ends up well over 15 MB.

    Decision · agreed

    Tailscale is the preferred transport and identity, never a requirement. Listen addresses are explicit in server config (the node's 100.x address, 0.0.0.0 inside a Nomad task with a Tailscale sidecar, or a LAN address). Two agent authentication modes are enabled together and chosen per connection:

    • Tailscale. When the peer address is a tailnet address and a local tailscaled socket exists, the server asks /localapi/v0/whois?addr= which node is on the other end and uses the node name as the host identity; the agent's claimed host_id must equal it. Whois proves who a peer is, not that it belongs to the fleet (nodes shared in from other tailnets reach the listener too), so agents.tailscale.allowed_tags / allowed_users name the nodes trusted as agents: a node matching neither list is refused, and with both lists empty a new tailnet node registers as pending for an admin even under registration: auto. Transport encryption comes from WireGuard; TLS is optional.
    • Token. Everywhere else (private LANs, hosts without Tailscale, local development). buckle install agent --server … --token <bootstrap> enrols the host: on the first Hello the server exchanges the bootstrap token for a per-host token (random, stored hashed server-side, persisted by the agent at mode 0600) which identifies the host from then on; the bootstrap token can be rotated or revoked without touching enrolled hosts. Host identity is host_id from agent.yaml, else the system hostname. Transport is TLS on the gRPC listener: a certificate from config, or one the server generates on first start whose fingerprint install agent pins (--ca-fingerprint, printed by buckle server --print-fingerprint); plaintext needs both ends to say so explicitly: listen.tls.mode: none on the server and tls.insecure_plaintext: true with an http:// URL in agent.yaml (an https:// URL combined with insecure_plaintext is refused rather than silently downgraded).

    Agents never depend on the Tailscale binary: the tailscale fact provider yields null when it is absent and selectors fall through. The server runs on a tailnet in this deployment, but nothing in the protocol assumes it.

    Module rules the loader and validator enforce: the directory name must equal name; needs must resolve, form a DAG, and name modules that are selected on every host this module is (otherwise planning that host is an error naming both modules); every file is read with unknown fields rejected (deny_unknown_fields), including each task and health spec; a task is one kind key plus the reserved keys id, name, when, notify, tags, removal, retry; and after is reserved but not implemented (a task that sets it is rejected, see 04). A directory under modules/ without a module.yaml is not silently ignored: its module is indeterminate and resources recorded under that name are kept. Templates are the *.j2 files under a module's files/ directory (there is no separate templates directory); file.copy and file.template read their src relative to files/.

    Expressions: filt-rs for logic, Jinja for text

    Two languages, each doing the thing it is good at. filt-rs decides whether (module and task when, groups, phase selection, health assertions, ACLs). Templates decide what text (file contents and the string fields of task specs). A task string field is templated only when it contains {{ (or {%), so plain values cost nothing. A rendered field is then converted to the scalar type its schema declares when that type is not a string (an integer, number or boolean) and the text parses as one, so size_mb: "{{ vars.swap_mb }}" reaches the task as the number 512. Undefined variables are errors (strict mode), and secrets are refused in plain fields and in vars: only the few fields typed as secret-capable (06) keep their raw template for the task to open through a sink.

    filt-rs context

    Flat dotted keys over a case-insensitive map, exactly like mail-backup's Metadata. Buckle builds it from the facts tree, labels, groups, vars and (metadata-only) secrets:

    • host.id, host.labels.* (typed: canary=true is a boolean, rack=3 a number, rack="3" a string), host.groups (tuple)
    • host.facts.os.{family,id,codename,version,pretty_name,kernel}, host.facts.hardware.{arch,cpus}, host.facts.hardware.mem.total_mb, host.facts.hardware.swap.total_mb, host.facts.hardware.disk.<name>.{mount,fstype,total_mb,free_mb,free_percent} (root for /), host.facts.tailscale.{hostname,ips,tags,online}, host.facts.cloud.{provider,region,…}, and the other providers in 05. Facts are flat dotted leaves: a list can be tested with contains but not indexed, which is why providers also expose flat keys such as disk.root.free_percent
    • vars.* (scalars and lists)
    • secrets.NAME as a filt-rs Secret value (comparable, redacts to [REDACTED] if ever displayed), plus secrets.NAME.present and secrets.NAME.fingerprint (see 06)
    • task.kind, task.id, task.tags, module.name, module.tags for run-time selectors (buckle apply --select 'task.tags contains "network"'); tasks excluded by --select still count as desired, so their resources are never treated as orphans
    Decision · agreed

    Templates move from Go templates to Jinja2 (minijinja), and gotmpl leaves the dependency tree entirely. Two languages in total: filt-rs for logic, minijinja for text. The audit found 18 Jinja templates in infra-ansible, two of them 550 and 819 lines, using .items(), default, regex_replace, to_json, ternary, comment and whitespace control. With minijinja plus a dozen custom filters they port almost verbatim. minijinja is a small, well-maintained crate with no runtime dependencies, supports a custom object model (needed for secret-aware rendering) and can be sandboxed (no includes outside the module).

    Everywhere v1 rendered with gotmpl (file templates, and the interpolation of task string fields and vars in v2) now goes through one minijinja Environment per revision, with the same filter set and the same secret-aware object model. The buckle migrate helper converts v1 .tpl files' {{ .KEY }} references to {{ vars.KEY }}.

    Vars, facts and secrets precedence

    1. Facts (host.facts.*) are read-only and collected by fact providers.
    2. Module vars: defaults.
    3. Fleet vars overlays in list order; an overlay without when always applies, its when may read facts, labels, groups and the vars layered so far, and an omitted vars is the empty set. An overlay is inline values or a file; the file path is relative to the repository root and must stay inside it (absolute paths and .. are rejected when the revision loads), and it must contain a mapping.
    4. Agent-local overrides from /etc/buckle/agent.yaml (vars:), for the rare host-specific value.

    Values are typed YAML (strings, numbers, bools, lists, maps), so a template loop over a list of snapshot paths is a real loop rather than Python repr hoping to be TOML. Vars can reference other vars and facts with templates; each var is rendered lazily after the vars it references, a reference cycle is an error that names the cycle, and vars cannot reference secrets. A reference to an undefined var or fact, or a template that does not render, is a plan error scoped to the module that uses it (the Ansible undef() behaviour, made explicit): the plan lists the module as indeterminate with plan_error set, applying reports it failed, and the other modules still plan and apply. When the failing template reads facts that a module this one needs will provide during the same run (facts.provides), the module is deferred until those facts are refreshed instead of failing on a first install.

    04

    Execution engine: plan, apply, remove

    The engine is the same code in buckle apply, in the agent, and in server-side plan previews. It is a pipeline whose first half is pure (reads only) and whose second half is driven entirely by the plan the first half produced.

    Scheduling

    • Modules form a DAG from needs. Independent modules run concurrently, bounded by the engine's parallelism (the CPU count; there is no command-line flag for it).
    • Tasks within a module run strictly in order, one at a time. after: is reserved but not implemented: a task that sets it is rejected by buckle validate and at plan time, with advice to order the tasks instead, rather than silently ignored.
    • Locks. Each task kind declares the resource locks it needs (apt.* → apt; systemd.* → systemd; the table is in section 05). The scheduler serialises holders of the same lock across modules, so docker and nomad install packages one at a time while their file tasks overlap. The editors of shared files (file.line, file.block, ssh.authorized_key) additionally hold a per-path lock inside the task, because kind locks are static: two modules editing /etc/ssh/sshd_config never lose each other's line.
    • Fact refresh and deferral. Vars and task fields are rendered lazily, per module, when that module is planned, so a render failure is scoped to its module, and a rendered string takes the scalar type the kind's schema declares (section 03). A module that declares facts.provides: [tailscale] causes those providers to re-run after it applies, before its own health checks; modules that need it are planned afterwards. A dependent whose vars, fields or when read facts such a provider will produce is deferred with the reason, instead of failing or being planned against stale facts: plan-only mode reports it as deferred, apply plans it once the facts are refreshed, and a deferred module whose when then turns out false is skipped and its resources are removed as orphans. A provider that fails keeps its last good value and is marked stale; one that has never produced a value makes the modules reading it indeterminate (below).
    • State is saved after every step (and every removal), atomically, so a crash costs at most the step in flight. A failed save is reported on the result; it never turns a change the host already took into an error.

    Handlers

    • Only steps that really changed something notify. A step that was planned as a change but whose apply reported no change does not fire its handlers, and a no-op never does.
    • Deduplicated by (kind, target) and ordered daemon_reload → restart → reload → everything else in notification order; a restart of a unit subsumes a reload of the same unit. Two handlers that restart nomad are one restart.
    • Module-scoped. docker and nomad each restarting nomad is two explicit declarations, not a name collision, and a task may notify another module's handler as nomad:restart. When the owning module has not started and needs the notifying module, the notification waits and runs once at the end of the owner (with the owner's vars, deduplicated against its own); otherwise it runs at the end of the notifying module. If the owner never runs (the run halted, or it turned out unselected) the handler still runs at the end of the run, because the change that notified it was made. A plan shows a cross-module handler under the module it will run in.
    • Removals run the handlers their task notified (the names are kept in state beside the resource), once, after the removals, and only those that still exist in the revision.

    Selection safety

    Removal makes a wrong "not selected" expensive, so the planner never guesses. A module's selection is indeterminate, not false, when its when cannot be evaluated; when it reads facts of a provider that failed without ever producing a value (or host.groups while some group's membership is uncertain for that reason); when its vars cannot be rendered and its when reads vars; when its directory has no module.yaml; or when it needs an indeterminate module. An indeterminate module is never applied and everything recorded under its name is kept: it is left out of the orphan computation, listed in Plan.indeterminate with the reason, repeated in the plan's warnings, reported as a warning by buckle validate --facts, and reported by apply with status indeterminate. A module that is selected but cannot be planned (a var or field does not render, a task kind does not support the platform, planning a task errors) is recorded the same way with plan_error set: applying reports that module failed and the run unsuccessful, nothing of it runs, its resources are kept, and the other modules still run. A task whose own when cannot be decided is kept in the desired set, so its resource is not an orphan, but is not planned, with a warning.

    A task kind that does not support the host's platform is a plan error naming the kind and advising a when, scoped to its module like any other. buckle validate --facts judges the platform from the facts file's os (a Debian fixture plans as Linux even when validation runs on macOS).

    Plan mode cannot write

    Planning may read anything and run read-only probes (unless, version checks), but everything that runs in plan mode goes through a guard that refuses writes, permission changes, removals, symlinks and renames outside the system's temp directory and the agent's scratch directory <state_dir>/tmp (where validate: commands get their private copies). A task that writes while planning fails loudly as a bug in the kind instead of changing a host during a "dry" plan or a server preview.

    Blocked steps

    A task whose tool is missing (no apt-get, no systemctl as PID 1, an explicit validate program that is not installed yet) plans as Blocked with the reason, not as an error, so a plan can be read on any machine. At apply, a blocked step is planned again once anything earlier in the run changed, because an earlier step may have installed the tool. If it now plans a change that deletes nothing, the change is applied and the handlers it notifies run with the planned ones; a deletion was never reviewed, so it stays blocked. A module that ends with blocked steps has status blocked; nothing failed and nothing is rolled back, but the revision is not fully applied, so the run is not a success: its recorded outcome is needs_attention and the server marks the host for an operator.

    Agent state and removal

    Every applied task writes a ResourceRecord to <state_dir>/state.cbor (CBOR; a 0600 temp file in the same directory, fsynced, renamed over the old file, then the directory fsynced). The record is the memory that makes removal possible.

    On every plan, the engine computes desired = selected modules × their tasks and orphans = state − desired, leaving out the records of modules whose selection is indeterminate, deferred or held, and the records that were re-homed (below). Each orphan whose policy is Cleanup becomes a Removal step that calls the task kind's remove(record): delete the file we wrote (only if its digest still matches what we wrote, otherwise flag drift and leave it), disable and stop a unit whose file we created, remove an apt repository we added, drop a sysctl line, revert a file.line. Removals run after all applies and only when nothing halted, dependents before their dependencies, and then run the handlers the original task notified.

    Re-homing. A changed config must not delete what a new resource now manages. Before computing orphans the engine matches each record that left the desired set against the desired resources. A task that moved to another module (same kind and key) has its record re-keyed to the new module and kept, with its original introduced_in and shadow, and the moved task plans against that record. A task re-keyed to another kind or key that manages the same artefact (a file.copy replaced by a file.template of the same path; the same package, user, unit or line) supersedes the old record, which is forgotten without running its cleanup, since that cleanup would delete what the new resource manages. Both are listed in Plan.rehomed and as "not removed" warnings.

    Decision

    Everything Buckle applied is removed when it leaves the config, unless the author opts out. The default is removal: cleanup for every task kind: files, units (disable, stop, delete the unit file Buckle wrote), apt repositories and packages, users and groups, sysctl entries, ufw rules, cron jobs. The exceptions are the handler-style kinds (apt.update, systemd.daemon_reload, systemd.restart, systemd.reload), which have nothing to undo and default to leave. command.run is the one kind that cannot infer an inverse; it cleans up when the author gives a remove: command (and must then carry an explicit id, because it is otherwise keyed by its rendered command and editing the command would run the old remove:) and is otherwise reported as no cleanup defined. Opt out with removal: leave, which records the resource as released rather than deleted. The policy that applies is the task's own removal, else the module's removal.policy, else the kind's default.

    Removals are always flagged as warnings in the plan and in the UI: each one is listed with the module it belonged to, the revision that introduced it, what the kind will do (apt remove nomad, userdel --remove sierra), and the kinds whose removal can take unrelated things down (packages, users, groups) get an explicit caution. approval: if_destructive treats a plan with any cleanup removal, or any step that deletes, as destructive, so a phase with that policy stops for sign-off whenever a module or task disappears. Local mode prints the same warnings and buckle apply asks for confirmation before removing a package, user or group unless --yes is given (without a terminal and without --yes it refuses).

    Drift

    The agent re-plans the revision it has applied every drift.interval and runs its applied modules' health checks in the same pass (section 07). A non-empty plan means something changed under us. With drift.correct: true the agent applies it (and reports "corrected drift" with the diff summary), unless the host is paused or a module was rolled back and the server has yet to decide; otherwise it reports drift and the host shows amber in the UI. External edits to a file Buckle manages are visible as a diff against the recorded shadow, which also tells the operator exactly what the hand edit was.

    The pass plans in drift mode, because a revision can be partly applied: a failed run leaves the host's applied revision behind while the modules that succeeded moved on, and a rolled-back module is back on the stable revision. State therefore records per module the revision it last applied and the revision it last failed on. Drift mode plans only the modules applied at the revision being checked and lists every other module (applied at another revision, failed last time, never applied) in Plan.held with the reason, leaving it alone; and it never treats a resource recorded at another revision as an orphan. The agent's unattended correction never executes removals at all, so an uncertain selection cannot delete anything and only an operator-approved apply removes (removals still appear in the drift plan).

    Failure handling

    • Module-scoped rollback, then halt. When a module fails, either because a task or handler errors or because one of its required health checks stays failing past settle after the module (and its handlers) applied, the run halts: modules already running drain, nothing new starts, removals are skipped, and each failed module is rolled back from the stable revision. The rollback follows the stable revision's own view of this host: it evaluates the stable revision's selection with the current facts; when the stable revision selects the module it is re-applied from it (files, units, handlers, health) and recorded at the stable revision, and when it does not (the module is new in the failed revision) rolling back means removing what the failed revision put in place; the module's resources that the stable revision no longer wants are removed too, unless a resource of the stable revision took them over. If the stable selection of the module is indeterminate, or no stable revision is cached, nothing is rolled back and the failure is left for an operator. Modules that already applied and passed their checks stay. The result names the module and the checks or task that failed, and the recorded run outcome is one of failed, unhealthy, rolled_back (a rollback succeeded) or needs_attention. The agent does not continue past the failure on its own; that is the operator's call (section 10).
    • Retries are per task (retry: { limit: 3, delay: 5s }), kept from v1 but moved to the task level where transient failures actually happen (downloads, apt locks).
    • Health settle. A module's checks run as soon as it and its handlers complete (the providers it declares in facts.provides are refreshed first, and the checks see the facts refreshed so far, not the plan-time snapshot), so a failure is attributed to the module that caused it. When the module changed something, a failing required check is re-run at its interval until settle (default 2 m) has elapsed since its first failure, so a restarting service is not blamed; failing past that marks the module unhealthy and triggers the rollback above. A module that changed nothing runs its checks once and reports them without gating, since nothing this run did can have broken it, and waived checks (a continue) report but no longer count. The agent then keeps checking for the bake window after the whole run, and the same rollback applies if a required check fails past settle there (section 08). The server treats unhealthy like failed for rollout purposes.
    • Plan errors and blocked steps do not halt the run (nothing of the module ran); they make it unsuccessful: failed for a module that could not be planned, needs_attention for blocked steps.
    • command.run is the escape hatch and is designed to stay plannable: creates:, unless: (a probe that runs in plan mode) or changed_when: make it idempotent, and a command without any of them is reported in the plan as always runs so the author sees the smell.

    Task, fact and health registries

    Three pluggable kinds, one recipe: a typed trait, an object-safe erased trait with a blanket impl, a Registration newtype, inventory::collect!, a register_task! macro, and a LazyLock registry that refuses duplicates. This is the automate pattern, which is the git-tool pattern with a type-erasure layer.

    Decision

    Fact providers never fail a run, and a guess is never a removal. A provider error keeps its last good value and marks the provider stale, with a warning span; a provider that has never produced a value is unavailable. Selectors that read an unavailable provider are uncertain, so the modules that depend on them are indeterminate (section 04): not applied, and their resources kept, rather than silently unselected and removed. A provider that answers successfully with null (no cloud, no Tailscale, no Nomad) is a normal fact, so the author still writes host.facts.cloud.provider == "oci", which is false there.

    06

    Secrets that cannot leak by accident

    Module authors and operators are trusted; the threat is accidents, not exfiltration. The goal is therefore structural: no code path formats, logs, serialises, diffs or displays a secret value, and the type system enforces it so a future contributor cannot leak one by mistake. Values exist in plaintext in exactly two places: inside the sealed Secret and inside a sink's write call, and every sink is greppable by its Witness.

    Rendering templates twice

    minijinja sees secrets as a custom object. In Mode::Redacted the object renders as «secret:nomad_server@3f9a»; in Mode::Real the renderer, which is itself a sink, reveals the value. The real render is returned as Sensitive<String>, which can only be written to disk or compared by digest. The redacted render is a plain Redacted<String> and becomes the shadow in state and the text shown in plans. A template that touched a secret always yields Sensitive output, and the taint cannot be laundered through an intermediate var because there is no way in: secrets are refused in vars and in ordinary task fields (a plain render that reaches one is an error). Only the few fields typed as SecretField keep their raw template through spec rendering (the schema marks them x-buckle-secret) and are opened by the task itself through a sink: the values of command.run env, user.account password, file.download and http check headers, and apt.repository auth.password.

    What the operator sees

    - servers = ["«secret:nomad_server@3f9a»"] + servers = ["«secret:nomad_server@b21c»"] datacenter = "dc1" - node_class = "cloud" + node_class = "rpi"

    A rotated secret shows up as a fingerprint change on exactly the lines that use it; everything else in the diff is real. That holds while the file on disk is still what Buckle wrote (its digest equals the one recorded at write time). A file that contains a secret and has drifted on disk shows content changed (digest 9a1f… → 02c7…) with a redacted preview of the new content rather than the hand edit, because reading the file back would mean handling plaintext outside a sink.

    Decision

    Secrets are resolved on the server and delivered per host, scoped to the modules the host selects. Agents hold no provider credentials. The server evaluates each host's module selection with the host's last reported facts, collects the secret references those modules use, resolves them and sends values inside the assignment over the Tailscale-encrypted stream. If an agent's local evaluation selects a module the server did not predict (facts changed), it asks for the missing names and the server checks the request against the revision before answering. In local mode (source: DIR in agent.yaml) the agent resolves with its own providers.

    Decision · agreed

    Filters see secrets as filt-rs Secret values. Authors are trusted, so secrets.NAME == "x" and the other comparisons work in when expressions; filt-rs's secrecy feature renders the value as [REDACTED] on Display and Debug, so a selector that ends up in a log or a plan cannot carry it. secrets.NAME.present and secrets.NAME.fingerprint remain for the common "is it configured" and "did it rotate" cases. Filter error messages contain only filter text, never target values, so a bad expression is safe to show in the UI.

    Decision · agreed

    Providers for v2.0 are file and env; Nomad delivers the values. The server's Nomad job uses template stanzas over Nomad Variables (or Vault) to render one file per secret into the task's secrets directory, or env = true to inject them as environment variables; buckle.yaml references them with { file: /secrets/NAME } or { env: NAME }. Nomad re-renders on variable change and can signal the task, so rotation needs no Buckle-side integration. The file provider re-reads on each resolution (no caching), and values are trimmed of a single trailing newline. exec exists only behind an explicit allowlist for local development, where op read is convenient: secrets.providers.exec.allow in server config, or --allow-secret-exec PROGRAM on a local-mode agent. It is off by default and not part of the production story. Agents resolve nothing themselves in server mode.

    Every other place a value could surface

    • Host diffs. When a task diffs a text file on the host (file.copy, file.template, file.line, file.block, cron.job, ssh.authorized_key), the unified diff is first run through the scrubber, which knows every secret value the host holds and searches for each in its plain, JSON-escaped, URL-encoded and base64 forms (base64 only where the secret starts the encoded block; hex and shell quoting are not recognised), so a secret already sitting in the file shows as its token. Files that are sensitive by path (/etc/environment, /etc/fstab, the shadow files, sudoers, anything under /etc/ssh or /etc/netplan, ~/.ssh/*) get zero-context diffs, changed lines only, and a file whose recorded shadow ever held a secret token never has its current content shown.
    • The file.line stash. The text a line edit replaces in a sensitive file is not kept in agent state, which is reported to the server: it goes to a 0600 file named by its digest under <state_dir>/stash/file.line/, and the record keeps only the digest, so removal can still restore the original line.
    • Command output. What command.run prints is scrubbed before it reaches a span, an error or a plan, and when its environment carried a secret it is not captured at all unless the task sets capture: always. A validate command's output is withheld when the file under test contains secrets.
    • Health reasons. A failing check's reason (a command's stdout, an HTTP body that echoes a secret) goes through the same scrubber before it leaves the check, so neither the UI, the server's health events nor the logs carry it.
    • At rest on the agent. The state directory is mode 0700 (on Windows an ACL restricted to Administrators and SYSTEM); the per-host token, the install key and agent.json are 0600; the cached secrets are 0600 CBOR with an HMAC tag that detects truncation or substitution. The cached stable revision's tree is verified against stable_tree_digest, the digest of the stable tarball that Welcome and HostUpdate carry, and so is every re-fetch of it, so a damaged or swapped cache is fetched again rather than applied.

    Providers and delivery

    • file confinement. With secrets.providers.file.root set, relative paths resolve under it and anything that leaves it is refused: an absolute path elsewhere, a .. component, or a symlink that resolves outside the (canonicalised) root. Without a root the server warns at start-up that fleet secrets may read any file it can.
    • env allow and deny lists. secrets.providers.env.allow (when set, the only variables that may be read) and deny take exact names or a prefix ending in *, and deny wins. The server never hands out its own credentials whatever the lists say: BUCKLE_*, OIDC_CLIENT_SECRET, GIT_TOKEN, GIT_WEBHOOK_SECRET, the OTEL_EXPORTER_OTLP_*HEADERS variables, and every variable server.yaml itself interpolates with ${{ env.NAME }}.
    • Scoped delivery and FetchSecrets. Each host receives only the secrets referenced by the modules its labels, facts and groups select (their task specs, handlers and templates) and by the vars overlays that match it. A when that tests a secret is evaluated on the server with the resolved value, so a module's secrets go only to the hosts the module selects. FetchSecrets (like FetchRevision and FetchBlob) answers only for an active host and only for the stable revision or a revision one of its rollouts assigns it; it returns just the requested names that the revision declares and that the host's own selection references, and silently grants nothing else. The fingerprint travels with each value, so a rotation yields the same plan digest on every host that uses the secret.
    • Local mode. buckle plan and buckle apply resolve secrets: with the env and file providers of the invoking process. An agent that watches a local directory resolves with the same two, and with exec only for the programs named on its command line, buckle agent --allow-secret-exec op (repeatable; refused for an agent that talks to a server, and never read from agent.yaml). An exec reference runs the exact allow-listed program with stdin closed, a 30 s timeout, and quotes only stderr in an error.
    07

    Health checks

    Health is part of the module, not a separate monitoring system. Checks run when a rollout needs an answer (was this host healthy before we touched it, did the change leave it working, are the hosts we already changed still fine before we go further) and once alongside each periodic drift check, so the server always holds a recent baseline for the whole fleet. There is no separate health loop; uptime monitoring stays with Grey.

    1 · Baseline, before apply

    When a host's wave is due, the server sends RunHealth { scope: baseline } and the agent runs the checks of the modules it currently has applied. A failing baseline holds the host: the rollout does not touch an already-unhealthy host unless an operator forces it (force apply in the UI, audited). This separates "the change broke it" from "it was already broken".

    2 · Bake, after apply

    Once ApplyResult arrives, checks for every applied module run at their interval (default 30 s) for the phase's bake duration, then stop (a required check that is still failing keeps being sampled past the window until it recovers or fails past settle). A required check that stays failing for longer than settle (default 2 m, flap tolerance for services restarting mid-rollout) marks the host unhealthy, counts against max_failures, and pauses the rollout on breach; a check that recovers inside the settle window is recorded as a flap, not a failure. The agent does not wait for the server: the same failure rolls that module back to the cached stable revision on the host (section 04) and is reported as a durable module rollback. min_uptime on the systemd check catches crash loops inside the window.

    3 · Pre-phase, before advancing

    Before the next phase starts, the server sends RunHealth { scope: rollout } to every host this rollout has already updated and waits for all results. A regression anywhere pauses the rollout instead of advancing, so a slow-burning failure in the canary is caught before the fleet follows.

    4 · With each drift check

    Every drift.interval (default 15 m) the agent already re-plans the revision it has applied; it now also runs the checks of its applied modules once and sends HealthReport { scope: drift } with the Drift message. This is the fleet's baseline health between rollouts: it drives the Overview roll-up, lets the UI show a host as unhealthy before anyone starts a rollout, and lets the controller pre-flag hosts that will be held at baseline. The pre-apply baseline check still runs fresh when the wave is due; the drift report is a recent reading, not a substitute.

    Check kinds

Every spec rejects unknown fields, and a check returns pass, fail or unknown; unknown means the check itself could not run (a missing tool, an unsupported platform, an expression that does not parse) and never fails a run.

    Session rules

    • Identity. On connect the server authenticates the peer by Tailscale whois when it can and by per-host token otherwise (both modes are always on; the decision card in 02 has the enrolment flow). Under whois the agent's claimed host_id must match the node name; under token auth the identity is the one bound to the token at enrolment. Labels come from two places: the agent reports its seed labels on connect, and operators manage server-side labels per host in the UI (stored in the database, never in server config). Server labels win on conflict, so an agent cannot promote itself out of the canary phase; the UI shows both sets and which one is effective.
    • Registration. A host the server has never seen is created on first Hello. With agents.registration: auto (the default) it is active immediately, except that a tailnet node no agents.tailscale list admits registers as pending; with approve (recommended for token auth) every new host sits as pending, visible in the UI, excluded from rollouts until an admin approves it. A pending host still connects, but receives no secrets and cannot fetch content. Admins can also pause a host (kept in the fleet, excluded from rollouts and drift correction), resume it, or forget it (removes its record and closes its live session; a reconnecting agent registers afresh). Approving, pausing, resuming and editing labels reach a connected agent at once as a HostUpdate, without a reconnect. The enrolment rules are in section 09.
    • Stable revision cached locally. Welcome and Assign name the fleet's current stable revision; the agent keeps that revision's tree and its scoped secrets in the state directory (secrets at mode 0600, the same trust level as the files they render) so it can apply it with no server at all. See the local rollback rules in section 10.
    • Reconnect. Exponential backoff 1 s to 5 min with jitter (mail-backup's reconnect_min/max). A new stream must send Hello within 30 s, and the agent gives up on a session that has not been answered with a Welcome within 30 s and reconnects with backoff. On reconnect the agent sends Hello with its applied revision, the digest of its last plan and unreported_apply_revisions, and the server resumes the host's rollout state from there rather than restarting it. A server that refuses the host outright (Rejected { retry: false }) does not stop the agent, which a service manager would only restart every few seconds: it keeps retrying with its own backoff from 1 s doubling to 1 h, and when the stored per-host token was refused and a bootstrap token is configured the next attempt presents the bootstrap token, so a forgotten host registers afresh (and goes back to the stored token if that is refused too). Rejected { retry: true } retries on the normal schedule.
    • Assignment is not apply. Assign tells the agent what to fetch and plan. Only Apply with a matching plan digest mutates. If the agent's fresh plan digest differs from the approved one (the host changed in between), it refuses and reports stale plan; the server re-requests a plan and, if the phase requires approval, the UI shows the host as needing re-approval.
    • Requests are bound to their session. Plan, health, apply and rollback requests belong to the session that sent them. If that session ends before the agent starts one, the agent drops it without a report and the server re-sends it after the reconnect: an Apply goes out again with the same plan digest and approval token, at most three times before the host is failed, unless Hello shows the target revision already applied or lists it in unreported_apply_revisions (the apply is running, or its result has not been acknowledged), in which case the server waits for the result instead. An apply that has started runs to completion whatever happens to the session, and its result is durable. A host that stays in applying for longer than agents.apply_timeout (default 30 min, counted from the Apply being sent or re-sent) without an ApplyResult counts as failed for the rollout, and so does one that stays disconnected mid-wave for longer than agents.disconnect_timeout (default 10 min).
    • Durable reports. ApplyResult and LocalRollback carry a report_id, monotonic per agent. The agent writes each one to agent.json before sending it, keeps it until an Ack names the id, and re-sends every unacknowledged report after each Welcome. The server records each (host, report_id) once, in the same transaction as the report's effects, and acknowledges duplicates too, so a dropped connection or a server restart can neither lose a result nor apply it twice. Reports from older agents carry id 0 and are not deduplicated.
    • Bake failures roll the module back. While it answers a bake request the agent tracks the failure streak of every required check; one that fails continuously for settle (default 2 m) rolls that module back on the host to the cached stable revision (planned with a module selector, applied through the engine), after which the agent makes no further changes and the server decides. The rollback is reported as a durable LocalRollback that names the modules and the failing checks, and says whether the rollback itself succeeded; if it did not, the rollout host is marked as needing attention with both results recorded. A failing check keeps being sampled past the bake window until it recovers or fails past settle, because the server judges it on the same clock.
    • Backpressure. ApplyEvents are coalesced to at most 10 per second per host; the server stores the last event per step and the full stream goes to tracing.
    • Versioning. Hello carries the agent version; the server refuses agents older than agents.minimum_agent_version (checked before anything is written, so a refused old agent can enrol once it is upgraded) and the UI shows version skew. Protobuf field numbering keeps older servers working with newer agents within a major version: the messages and fields added since the first draft (Ack, HostUpdate, report_id, needs_attention, module_errors, Apply.select, Welcome.stable_tree_digest, unreported_apply_revisions, the traceparent fields) are all additive, and an older agent simply never acknowledges or reports what it does not know.
    • Self-update. Buckle uses update-rs's GitHub release source and asset naming for both buckle update [--to VERSION] on the command line and the agent's handling of Upgrade: it downloads the release asset for its platform, refuses it unless GitHub reports a SHA-256 digest and the download matches, renames the new binary into place beside the running one (on Windows the running image is moved aside first) and exits, so systemd, launchd or the Service Control Manager restarts it, and it reconnects with the new version in Hello. An Upgrade sent when_idle waits until the agent has nothing queued. The relaunch machinery of update-rs is not used, because its detached processes would be killed with the service's cgroup. The server side is not built: agents.desired_version is accepted in server.yaml, but nothing yet sends Upgrade (no phase-ordered pacing, no UI trigger), so fleet upgrades are driven by running buckle update on the hosts.
    • Local mode implements the same Transport trait with a filesystem watcher (notify): a change that has settled for 2 s is an Assign of a synthetic revision (its id is the digest of the tree) followed by a plan and an automatic apply, and reports are logged. The agent resolves the fleet's secrets itself in this mode (section 06).

    Server: revisions, Git, persistence

    The server is three loops sharing one SQLite database: a source watcher that turns commits into revisions, a rollout controller that moves hosts through phases, and the gRPC and HTTP fronts that feed them.

    Source watcher

    • A bare clone under data_dir/source.git managed with gix, fetched every poll (default 30 s) and immediately on POST /api/v1/webhooks/source (HMAC-verified, for a GitHub webhook over Tailscale Funnel or a Nomad-local forwarder).
    • Change detection compares the remote-tracking ref for the configured branch before and after the fetch (the audit of github-backup found that comparing HEAD misses remote-only updates), and then with the last commit it processed.
    • Every new commit on the branch becomes a revision, oldest first, so each one is validated and visible in the UI and the rollout controller supersedes the older ones (up to 50 commits per fetch: a longer gap, or a tip that does not descend from the last processed commit through first parents, builds the tip only). A branch that moves back to a commit already built (a force-push, or a reverted ref) is announced again, so the fleet converges on the branch tip rather than staying on a revision the branch no longer points at. A fetch is interrupted after source.git.fetch_timeout (default 2 m) and retried at the next poll.
    • Each commit is exported to data_dir/revisions/<id>/, loaded and validated (schema with unknown fields rejected, selectors parse, templates parse, unique module names, needs resolve and form a DAG, rollout phase names unique and not stragglers, every referenced secret declared) and stored as a Revision: commit id, author, message, timestamp, a content-addressed gzip tarball of buckle.yaml, modules/ and vars/ (with a digest the agent verifies, and an index of its files by digest for FetchBlob), and the validation report. Invalid commits are stored as rejected revisions so the UI can show the author what broke, and the fleet stays on the last valid one. This check is narrower than buckle validate, which also resolves task and health kinds, handler references, after: and the command.run id rule and, given --facts, dry-plans each fixture host: run it in CI, because a revision with an unknown task kind is accepted by the server and fails as a plan error for that module on the hosts that select it.
    • A path: source (local directory with a filesystem watcher) is supported for development and for a server fed by a CI job that already checked out the repo.

    Enrolment and trust

    • No takeover. A bootstrap token only creates hosts. If the claimed host_id is already registered, whether it enrolled with a token or registered over the tailnet, enrolment is refused ("present its per-host token, or forget the host in the UI to enrol it again"); a forgotten host has no row and enrols afresh. Symmetrically, a host that enrolled with a token keeps authenticating by its token even when a tailnet node bears its name, so a node name cannot stand in for the token.
    • Throttled. Anything that is not a recognised per-host token counts as a bootstrap attempt, limited to 10 per peer address per minute, compared in constant time; the claimed host_id must be 1 to 128 characters of letters, digits, ., _ and -. Per-host tokens are random 32 bytes, stored only as a SHA-256 hash.
    • Version first. agents.minimum_agent_version is checked before anything is written, so a refused old agent leaves no half-enrolled record and can enrol once it is upgraded.
    • Tailnet trust. Whois proves who a peer is, not that it belongs to the fleet. With agents.tailscale.allowed_tags or allowed_users set, a node matching neither is refused outright, registered or not; a matching new node registers according to registration. With both lists empty nothing is trusted to activate itself: a new tailnet node registers pending and waits for an admin, exactly as under approve, and the server warns at start-up when that is the case.
    Decision · agreed

    HTTP on actix-web, gRPC on tonic, in one process. actix-web is what automate and analytics use, so the OIDC middleware, the TracingLogger transform, the embedded-UI serving and the test harness port over directly. tonic runs on the same tokio runtime on its own port. Both shut down on SIGTERM; the rollout controller checkpoints host state on every transition so a restart mid-rollout resumes rather than restarts.

    Controller algorithm

    1. Freeze the target set. When the rollout starts, evaluate every phase selector against the current fleet (connected or not) and store the host-to-phase assignment with the rollout. A host matches the first phase whose selector is true and belongs to that stage only; it is never listed or re-applied in a later stage, even when that stage's selector would also match it. Hosts that miss their phase (offline during their wave, plan still pending, enrolled after the freeze, held at baseline and released later) are not lost: they move to the virtual stragglers stage, which runs after promotion (step 7).
    2. Plan everywhere first. Send Assign + RequestPlan to all targeted hosts up front, in parallel. Plans arrive over the following seconds; the UI groups them by digest. Disconnected hosts show as plan pending and do not block earlier phases.
    3. Gate. If the phase's approval policy requires it, wait for an approval that binds the phase's plan digests. A host whose plan changes after approval (stale) drops back to needs approval for that host only.
    4. Baseline. Before a host's wave starts, run the health checks of what it currently has applied. Unhealthy → the host is held per health.baseline (default: wait for an operator to force or skip it); the wave fills from the next host so one sick machine does not stall the phase.
    5. Waves. Apply to parallel hosts at a time. A host is done when ApplyResult is success and its bake window passed without a required check failing. Failures count against max_failures; on breach the phase enters Paused and nothing else is started.
    6. Bake. Each applied host repeats its checks for bake; the phase is baked when its last host is. Regression → Paused. Checks stop when the window closes.
    7. Pre-phase gate. Before advancing, re-run health on every host already updated by this rollout and wait for all results. Any regression → Paused, naming the host and check.
    8. Advance. Next phase. After the last phase bakes and its pre-advance check passes, the revision becomes stable: the revision new and reconnecting hosts converge to.
    9. Stragglers. Promotion opens a virtual final stage on the rollout holding every targeted host that was not updated during its phase, plus hosts enrolled since the freeze. Each is applied with the stable revision as it becomes available (baseline check, apply, bake), stragglers.parallel at a time, and its result is recorded on this rollout so the UI shows them in one place rather than scattered across host pages. A straggler failure marks that host needs attention and never un-promotes the revision or pauses anything else. The stage stays open until the next rollout is promoted, which carries any still-unfinished stragglers into its own stragglers stage. A rolled-back or aborted rollout never opens the stage.
    10. Paused offers four operator decisions, each audited:
      • Retry: re-plan and re-apply the failed host as it stands (the failed module is back on the stable version, the rest of the run is still pending); the same checks apply.
      • Continue: retry the failed host with the specific checks that failed (module + check names) waived for this rollout on this host, so the run proceeds past that module and finishes the remaining modules. The waiver is carried in the Apply message, shown on the host in the UI, and expires with the rollout; the checks still run and report, but no longer count. A task error (as opposed to a health failure) has nothing to waive, so continue is offered only for health failures.
      • Rollback: apply the previous stable revision to every host this rollout already updated, newest phase first.
      • Skip or abort: exclude the host with a reason and go on, or stop the rollout where it is with state recorded.
      A host that rolled a module back (section 04) arrives here with that module on the stable version and the rest of its plan unapplied; a host that rolled its whole revision back while disconnected arrives on the stable revision, with its evidence attached to the pause.
    Decision · agreed

    Rollback means "apply the previous stable revision", not "undo the diff". Because revisions are content-addressed and cached on agents, rolling back is the same operation as rolling forward, including removal cleanup for resources the new revision added. This is predictable and cheap. The limitation is honest: an irreversible task (a package upgrade with a schema migration) rolls back only as far as the task kind can take it, and the plan for the rollback shows exactly that.

    Decision · agreed

    Agents can roll themselves back when a change cuts them off from the server. Each agent keeps the current stable revision (tree and scoped secrets) in its state directory. After applying a new revision the agent watches two things for local_rollback.after (default 5 m): whether the server session it had before the apply comes back, and whether required health checks stay failing beyond settle. If it was connected before the apply, cannot re-establish a session within the window, and (with on_health) health is also failing, it applies the cached stable revision on its own, records a LocalRollback in state with the evidence, and reports it on reconnect. While the server is reachable the agent never decides alone: the server has fleet context and owns pause and rollback. The server treats a reported local rollback as that host failing its wave, which pauses the rollout. settle exists because a restarting service legitimately fails its check for a few seconds; only a failure that persists through the window counts, whether the agent or the server is judging.

    Edge cases handled: the server itself going down right after an apply looks like connectivity loss, which is why connectivity alone does not trigger a rollback by default (the on_health condition must also hold); a rollback that itself fails leaves the host in needs attention with both results recorded; an agent restart mid-window resumes the window from persisted state.

    Decision

    The controller is a persisted state machine. Every transition is a row update plus an audit event, so a server restart or a Nomad reschedule resumes mid-rollout. The in-memory part is only timers (bake deadlines) and the set of connected streams, both rebuilt from the database and the reconnecting agents.

    Your call

    Fleet size here is four hosts, so parallel: 1 everywhere is plausible and phases are mostly about canary-then-rest. The design still supports percentages and failure budgets because they cost little and matter if the fleet grows. Should automatic rollback (on_failure: rollback) be the default, or pause-and-wait as proposed? Pause is safer when the failure might be the health check rather than the change; rollback is better when nobody is watching.

    Web UI and authentication

    The UI follows automate and analytics exactly: a Yew application compiled to WebAssembly with Trunk, hand-written SCSS, a framework-free buckle-api DTO crate shared with the server, embedded with include_dir! and served with an SPA fallback.

    Decision · agreed

    OIDC uses the analytics variant: server-driven Authorization Code + PKCE, HttpOnly session and refresh cookies, double-submit CSRF. Tokens never reach the browser's JavaScript. Routes: /api/v1/auth/login (takes return_to, honoured only when it is a local path starting with a single /; anything else lands on /), /callback, /refresh, /logout, /csrf; /api/v1/me always answers 200: the signed-in user, or, when OIDC is not configured, an anonymous: true placeholder whose is_admin says what admin_acl made of the request (older servers answered 204). Authorisation is two filt-rs ACLs over claims.*, client_ip, method and path: user_acl (may read; absent means every signed-in user) and admin_acl (may approve, reject, pause, rollback, and manage hosts: labels, registration, pause, forget; absent means nobody when OIDC is configured and everybody when it is not). client_ip is the peer address, or with web.trust_proxy the X-Forwarded-For entry web.trusted_proxy_hops places from the right, so entries a client wrote itself are never trusted. Omitting oidc disables authentication for local development, with the ACLs still evaluated against request metadata; the server warns at start-up about whichever combination leaves the UI open or shut. The sign-in endpoints are rate limited per client (IPv6 clients per /64, since one host can pick a fresh address for every request).

    The automate variant (popup + bearer token in sessionStorage) avoids CSRF handling but keeps an ID token in the page. For a tool whose buttons mutate production hosts, cookies with CSRF is the safer default.

    Observability

    tracing-batteries everywhere, with one rule that v1 did not have: a rollout is one trace. The server starts it, every agent continues it, and the UI links to it.

    Traces

    • rollout.run (server, root) → rollout.phase → rollout.host (one per host per wave) → the agent's agent.apply span, parented via traceparent (gRPC metadata, and a field on Apply, Rollback and RunHealth so a re-sent request keeps its parent) → engine.apply → module.apply (or module.rollback) → task.plan / task.apply → handler.run → removal.run → health.check.
    • Agent-initiated work (agent.drift, agent.watchdog) starts a fresh root per pass with parent: None and follows_from the agent.session span, the mail-backup pattern, so traces export promptly.
    • Span fields: buckle.revision, buckle.host, buckle.module, buckle.task.kind, buckle.task.key, buckle.changed (bool), buckle.plan.digest, buckle.phase, buckle.wave. Command stdout/stderr are recorded on command.run spans as v1 does, truncated at 4 KiB each and scrubbed of known secret values, and never when the command's environment carried a secret unless the task sets capture: always.

    Metrics (OTLP)

    • buckle.rollout.hosts gauge by rollout, phase and state: the hosts of every live rollout, sampled by the server every 15 s; a series that disappears is recorded once as 0 so dashboards do not keep the last value
    • buckle.agent.connected gauge on the server: agents with an open session
    • Not implemented yet: buckle.apply.duration (histogram by module and outcome), buckle.task.changes (counter by kind), buckle.health.status (gauge by module and check) and buckle.drift.resources (gauge per host). The same facts reach the server today as ApplyResult, HealthReport and Drift messages and as spans.

    Metrics go through the OpenTelemetry battery's meter provider (instruments are no-ops until an OTLP endpoint is configured). The endpoint comes from --otel-endpoint, the standard OTEL_EXPORTER_OTLP_* variables, or the telemetry.otlp_endpoint and otlp_headers keys of server.yaml and agent.yaml, in that order of precedence.

    Logs and errors

    human-errors throughout, with the user/system split deciding what counts as a bug: a template referencing an undefined var is a user error shown in the plan; a panic in a task kind or a corrupted state file is a system error sent to Sentry (optional battery) and surfaced in the UI as "needs attention". The agent writes structured logs to journald via tracing's stdout layer with OTLP as the primary path. The HTTP TracingLogger comes from automate with its query and header redaction lists.

    Known gaps

    Each of these is checkable in the repository; none is a design change. The first three are the tests recorded as ignored in crates/buckle-integration/tests/fleet (run them with cargo test -p buckle-integration -- --ignored); the rest follow from the code.

    • A phase over its failure budget can still promote. Section 10 says that when failures exceed max_failures the phase pauses and nothing else starts. Today, once the operator acts on a different host the controller resumes, and when that host finishes the phase counts the still-failed host as finished, passes its gate and promotes the revision with the breach unresolved (drive_phases in rollout/controller.rs treats Failed as finished). Test: a_phase_over_its_failure_budget_does_not_complete_while_the_failure_stands in gaps.rs.
    • A restart while a rollout awaits approval can promote it unapproved. The controller drives its phases as soon as it loads, before agents have reconnected, so every planned host counts as offline and the phase finishes with its hosts missed; the revision is then promoted without the canary's approval and the stragglers stage applies it. Test: a_rollout_restarted_while_awaiting_approval_still_awaits_it in durability.rs.
    • A rotated secret in a template. Section 06 promises a fingerprint change on exactly the lines that use the secret. a_rotated_secret_is_a_fingerprint_change_on_the_line_that_uses_it in gaps.rs is ignored on the grounds that file.template ignores the recorded shadow, but file.template now plans against the recorded shadow whenever the file is unchanged since Buckle wrote it. The ignore may be stale; re-run the test before counting this as open.
    • Deferred modules are applied unreviewed. Section 11 says that if a deferred module's eventual plan is destructive the agent stops and asks for approval. The executor plans a deferred module after the facts it waits for are refreshed and runs it, with the removals of its orphans, whatever it turns out to do; the approved digest covers the deferral, not the module's steps. Only a previously blocked step that now plans a deletion is held back.
    • Server-driven agent upgrades. agents.desired_version is parsed and shown in the configuration, but nothing constructs an Upgrade message, so the phase-ordered, idle-only upgrade of section 08 does not happen; the agent's handling of Upgrade and buckle update work.
    • Metrics. Only buckle.rollout.hosts and buckle.agent.connected exist; the apply-duration, task-change, health-status and drift-resource instruments of section 13 do not.
    • User documentation. The VuePress guide and reference pages planned for docs/ were not written; the documentation is this page, its README, the project README, the example's README and the generated buckle catalog.

    Testing conventions

    • Unit tests inline (#[cfg(test)] mod tests), rstest cases, descriptive sentence names, as in the reference repos. A System fake makes task tests hermetic; a container suite exercises the real thing.
    • Secret leak tests are property-style: for every type that can hold a secret, format with Debug and Display, serialise with serde_json and serde_yaml, record on a tracing span with the Testing battery, and assert the plaintext never appears.
    • Protocol tests run server and agent in one process over a real tonic channel (buckle-agent against a fake server, and buckle-integration against the real one); time is controlled with tokio::time::pause where bake, settle and backoff are under test.
    • Sign-in is tested in the server's web tests against an in-process wiremock identity provider. The UI's Playwright specs (ui/e2e) run the built UI against a small static server in demo mode, with fixtures and no server behind it.
