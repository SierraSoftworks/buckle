    Buckle v2: fleet configuration with phased rollouts

    A single Rust binary that runs as a planner, a persistent agent, or a rollout server. Modules declare idempotent tasks, health checks and cleanup; the server watches Git, ships revisions over Tailscale, and orchestrates feedback-controlled rollouts with a human sign-off gate on the plan.

    00

    What v2 is, in one screen

    Buckle v1 is a bootstrapper: it walks a directory of packages, writes files and runs scripts. Buckle v2 keeps that single-binary, zero-ceremony feel and becomes a fleet configuration system: declarative idempotent tasks, continuous agents, a Git-watching server, phased rollouts gated on health and human approval, and a UI to watch it all.

    Lightweight

    One static binary (musl) for agent and server. Agent idles at a few MB RSS: one gRPC stream, one timer, no interpreter. Bootstrapping is buckle install agent --server ….

    Fast

    Modules run as a dependency DAG with parallel execution; tasks declare resource locks (e.g. apt) so unrelated work overlaps. Plan is a pure read phase; apply touches only what changed.

    Observable

    One trace per rollout spanning server and every agent (W3C trace context in gRPC metadata and in the Apply, Rollback and RunHealth messages). Spans per module, task and health check with change counts; OTLP gauges for rollout hosts and connected agents; the UI shows the trace id and links it when a trace URL template is configured.

    Operable at scale

    Phased rollouts with bake time and failure budgets, automatic pause, one-click rollback to the last stable revision, drift detection and correction, and removal cleanup so hosts converge instead of accumulating debris.

    What changes from v1

    v1 is 1,400 lines of Rust: apply and plan commands over a Core with mockable Launcher, FileWriter and Output traits. Keep the spirit (trait-backed core, mockall tests, human-errors, tracing-batteries), replace the execution model.

    Decision

    v2 replaces v1 on main as Buckle 2.0.0. The v1 code is deleted rather than kept as a legacy mode; the migration helper and a documented mapping cover the transition. Keeping two engines in one binary would double the test surface for a tool with a small user base.

    02

    System topology

    One binary, three roles. The server is the only component with state about the fleet; agents hold only their own state. Everything between them crosses the tailnet.

    Processes and roles

    buckle plan / apply

    One-shot against a config directory, same engine as the agent. Used for authoring, CI validation and bootstrap before an agent is installed.

    buckle agent

    Long-running. Connects to a server (or watches a local directory), applies assigned revisions, runs health checks, reports facts and results, re-plans periodically for drift.

    buckle server

    Watches Git, builds revisions, orchestrates rollouts, serves gRPC to agents and the OIDC-protected HTTP API and UI to operators.

    Decision · agreed

    One binary, one build. The release artefact is the full buckle binary with agent, server and embedded UI; there is no slim agent variant. Target size is under 15 MB stripped (musl, LTO, codegen-units = 1, panic = "abort", release-mode Trunk build of the UI, symbols published separately as the reference repos do). CI reports the binary size per platform; a feature flag to drop the server from the agent build is reconsidered only if the full binary ends up well over 15 MB.

    Decision · agreed

    Tailscale is the preferred transport and identity, never a requirement. Listen addresses are explicit in server config (the node's 100.x address, 0.0.0.0 inside a Nomad task with a Tailscale sidecar, or a LAN address). Two agent authentication modes are enabled together and chosen per connection:

    • Tailscale. When the peer address is a tailnet address and a local tailscaled socket exists, the server asks /localapi/v0/whois?addr= which node is on the other end and uses the node name as the host identity; the agent's claimed host_id must equal it. Whois proves who a peer is, not that it belongs to the fleet (nodes shared in from other tailnets reach the listener too), so agents.tailscale.allowed_tags / allowed_users name the nodes trusted as agents: a node matching neither list is refused, and with both lists empty a new tailnet node registers as pending for an admin even under registration: auto. Transport encryption comes from WireGuard; TLS is optional.
    • Token. Everywhere else (private LANs, hosts without Tailscale, local development). buckle install agent --server … --token <bootstrap> enrols the host: on the first Hello the server exchanges the bootstrap token for a per-host token (random, stored hashed server-side, persisted by the agent at mode 0600) which identifies the host from then on; the bootstrap token can be rotated or revoked without touching enrolled hosts. Host identity is host_id from agent.yaml, else the system hostname. Transport is TLS on the gRPC listener: a certificate from config, or one the server generates on first start whose fingerprint install agent pins (--ca-fingerprint, printed by buckle server --print-fingerprint); plaintext needs both ends to say so explicitly: listen.tls.mode: none on the server and tls.insecure_plaintext: true with an http:// URL in agent.yaml (an https:// URL combined with insecure_plaintext is refused rather than silently downgraded).

    Agents never depend on the Tailscale binary: the tailscale fact provider yields null when it is absent and selectors fall through. The server runs on a tailnet in this deployment, but nothing in the protocol assumes it.

    Module rules the loader and validator enforce: the directory name must equal name; needs must resolve, form a DAG, and name modules that are selected on every host this module is (otherwise planning that host is an error naming both modules); every file is read with unknown fields rejected (deny_unknown_fields), including each task and health spec; a task is one kind key plus the reserved keys id, name, when, notify, tags, removal, retry; and after is reserved but not implemented (a task that sets it is rejected, see 04). A directory under modules/ without a module.yaml is not silently ignored: its module is indeterminate and resources recorded under that name are kept. Templates are the *.j2 files under a module's files/ directory (there is no separate templates directory); file.copy and file.template read their src relative to files/.

    Expressions: filt-rs for logic, Jinja for text

    Two languages, each doing the thing it is good at. filt-rs decides whether (module and task when, groups, phase selection, health assertions, ACLs). Templates decide what text (file contents and the string fields of task specs). A task string field is templated only when it contains {{ (or {%), so plain values cost nothing. A rendered field is then converted to the scalar type its schema declares when that type is not a string (an integer, number or boolean) and the text parses as one, so size_mb: "{{ vars.swap_mb }}" reaches the task as the number 512. Undefined variables are errors (strict mode), and secrets are refused in plain fields and in vars: only the few fields typed as secret-capable (06) keep their raw template for the task to open through a sink.

    filt-rs context

    Flat dotted keys over a case-insensitive map, exactly like mail-backup's Metadata. Buckle builds it from the facts tree, labels, groups, vars and (metadata-only) secrets:

    • host.id, host.labels.* (typed: canary=true is a boolean, rack=3 a number, rack="3" a string), host.groups (tuple)
    • host.facts.os.{family,id,codename,version,pretty_name,kernel}, host.facts.hardware.{arch,cpus}, host.facts.hardware.mem.total_mb, host.facts.hardware.swap.total_mb, host.facts.hardware.disk.<name>.{mount,fstype,total_mb,free_mb,free_percent} (root for /), host.facts.tailscale.{hostname,ips,tags,online}, host.facts.cloud.{provider,region,…}, and the other providers in 05. Facts are flat dotted leaves: a list can be tested with contains but not indexed, which is why providers also expose flat keys such as disk.root.free_percent
    • vars.* (scalars and lists)
    • secrets.NAME as a filt-rs Secret value (comparable, redacts to [REDACTED] if ever displayed), plus secrets.NAME.present and secrets.NAME.fingerprint (see 06)
    • task.kind, task.id, task.tags, module.name, module.tags for run-time selectors (buckle apply --select 'task.tags contains "network"'); tasks excluded by --select still count as desired, so their resources are never treated as orphans
    Decision · agreed

    Templates move from Go templates to Jinja2 (minijinja), and gotmpl leaves the dependency tree entirely. Two languages in total: filt-rs for logic, minijinja for text. The audit found 18 Jinja templates in infra-ansible, two of them 550 and 819 lines, using .items(), default, regex_replace, to_json, ternary, comment and whitespace control. With minijinja plus a dozen custom filters they port almost verbatim. minijinja is a small, well-maintained crate with no runtime dependencies, supports a custom object model (needed for secret-aware rendering) and can be sandboxed (no includes outside the module).

    Everywhere v1 rendered with gotmpl (file templates, and the interpolation of task string fields and vars in v2) now goes through one minijinja Environment per revision, with the same filter set and the same secret-aware object model. The buckle migrate helper converts v1 .tpl files' {{ .KEY }} references to {{ vars.KEY }}.

    Vars, facts and secrets precedence

    1. Facts (host.facts.*) are read-only and collected by fact providers.
    2. Module vars: defaults.
    3. Fleet vars overlays in list order; an overlay without when always applies, its when may read facts, labels, groups and the vars layered so far, and an omitted vars is the empty set. An overlay is inline values or a file; the file path is relative to the repository root and must stay inside it (absolute paths and .. are rejected when the revision loads), and it must contain a mapping.
    4. Agent-local overrides from /etc/buckle/agent.yaml (vars:), for the rare host-specific value.

    Values are typed YAML (strings, numbers, bools, lists, maps), so a template loop over a list of snapshot paths is a real loop rather than Python repr hoping to be TOML. Vars can reference other vars and facts with templates; each var is rendered lazily after the vars it references, a reference cycle is an error that names the cycle, and vars cannot reference secrets. A reference to an undefined var or fact, or a template that does not render, is a plan error scoped to the module that uses it (the Ansible undef() behaviour, made explicit): the plan lists the module as indeterminate with plan_error set, applying reports it failed, and the other modules still plan and apply. When the failing template reads facts that a module this one needs will provide during the same run (facts.provides), the module is deferred until those facts are refreshed instead of failing on a first install.

    04

    Execution engine: plan, apply, remove

    The engine is the same code in buckle apply, in the agent, and in server-side plan previews. It is a pipeline whose first half is pure (reads only) and whose second half is driven entirely by the plan the first half produced.

    Scheduling

    • Modules form a DAG from needs. Independent modules run concurrently (bounded by --parallelism, default CPU count).
    • Tasks within a module run in order. A task may set after: [id] to run concurrently with earlier siblings when order does not matter; this is rare and opt-in.
    • Locks. Each task kind declares the resource locks it needs (apt.* → apt; systemd.daemon_reload → systemd). The scheduler serialises holders of the same lock across modules, so docker and nomad install packages one at a time while their file tasks overlap.
    • Handlers are collected during apply and run once at the end of the module that owns them, deduplicated by (kind, target), ordered daemon_reload → restart → reload; a restart subsumes a reload of the same unit. Handlers are module-scoped, so docker and nomad each restarting nomad is two explicit declarations, not a name collision. A module may call another module's handler as nomad:restart.
    • Fact refresh. A module that declares facts.provides: [tailscale] causes those providers to re-run after it applies; modules that need it are planned afterwards. In plan-only mode they are reported as deferred with the reason, instead of being planned against stale facts.

    Plan data model

    buckle-core/src/plan.rspub struct Plan {

pub enum Diff {
    Create { summary: String, preview: Redacted<String> },

    Redacted<T> is a newtype that can only be constructed by the secret-aware renderer (section 06); the plan is therefore safe to log, serialise to the server and show in the UI by construction.

    Agent state and removal

    Every applied task writes a ResourceRecord to /var/lib/buckle/state.cbor (atomic write via temp file and rename, as mail-backup does). The record is the memory that makes removal possible.

    buckle-core/src/state.rspub struct ResourceRecord {
    pub key: ResourceKey,               // "nomad/file.template[/etc/nomad.d/nomad.hcl]"
    pub kind: &'static str,
    pub spec_digest: Digest,
    pub shadow: Option<Redacted<String>>, // redacted render of file content, used for plan diffs
    pub artefacts: Vec<Artefact>,       // paths written, packages installed, units enabled, users created
    pub removal: RemovalPolicy,         // Cleanup | Leave
    pub revision: RevisionId,
    pub applied_at: DateTime<Utc>,
}

    On every plan, the engine computes desired = selected modules × their tasks and orphans = state − desired. Each orphan whose policy is Cleanup becomes a Removal step that calls the task kind's remove(record): delete the file we wrote (only if its digest still matches what we wrote, otherwise flag drift and leave it), disable and stop a unit whose file we created, remove an apt repository we added, drop a sysctl line, revert a file.line. Removals run after all applies, in reverse dependency order, and notify the handlers the original task notified.

    Decision

    Everything Buckle applied is removed when it leaves the config, unless the author opts out. The default is removal: cleanup for every task kind: files, units (disable, stop, delete the unit file Buckle wrote), apt repositories and packages, users and groups, sysctl entries, ufw rules, cron jobs. command.run is the one kind that cannot infer an inverse; it cleans up when the author gives a remove: command and is otherwise reported as no cleanup defined. Opt out per task or per module with removal: leave, which records the resource as released rather than deleted.

    Removals are always flagged as warnings in the plan and in the UI: each one is listed with the module it belonged to, the revision that introduced it, what the kind will do (apt remove nomad, userdel --remove sierra), and the kinds whose removal can take unrelated things down (packages, users, groups) get an explicit caution. approval: if_destructive treats any removal as destructive, so a phase with that policy stops for sign-off whenever a module or task disappears. Local mode prints the same warnings and buckle apply asks for confirmation before removing a package, user or group unless --yes is given.

    Drift

    The agent re-plans against its assigned revision every drift.interval and runs its applied modules' health checks in the same pass (section 07). A non-empty plan means something changed under us. With drift.correct: true the agent applies it (and reports "corrected drift" with the diff summary); otherwise it reports drift and the host shows amber in the UI. External edits to a file Buckle manages are visible as a diff against the recorded shadow, which also tells the operator exactly what the hand edit was.

    Failure handling

    • Module-scoped rollback, then halt. When a module fails, either because a task errors or because one of its required health checks stays failing past settle after the module (and its handlers) applied, the agent re-applies that module from the previous stable revision (its files, units, removals and handlers), records the rollback against the module, and stops making further changes on this host: modules not yet started in this run are left untouched, modules that already applied and passed their checks stay. The run result is failed, naming the module and the checks or task that failed. The agent does not continue past the failure on its own; that is the operator's call (section 10).
    • Retries are per task (retry: { limit: 3, delay: 5s }), kept from v1 but moved to the task level where transient failures actually happen (downloads, apt locks).
    • Health checks run per module as soon as that module and its handlers complete (so a failure is attributed to the module that caused it), then keep running for the bake window after the whole run. A required check failing in either place triggers the module-scoped rollback above. The server treats unhealthy like failed for rollout purposes.
    • command.run is the escape hatch and is designed to stay plannable: creates:, unless: (a probe that runs in plan mode) or changed_when: make it idempotent, and a command without any of them is reported in the plan as always runs so the author sees the smell.
    05

    Task, fact and health registries

    Three pluggable kinds, one recipe: a typed trait, an object-safe erased trait with a blanket impl, a Registration newtype, inventory::collect!, a register_task! macro, and a LazyLock registry that refuses duplicates. This is the automate pattern, which is the git-tool pattern with a type-erasure layer.

    buckle-core/src/task.rs/// A typed, idempotent operation. Implementations are unit structs registered with `register_task!`.
pub trait Task: Send + Sync + 'static {
    /// Deserialised from the YAML under the task's kind key. Must be `JsonSchema`
    /// so `buckle validate` and editors get a schema for free.
    type Spec: DeserializeOwned + Serialize + JsonSchema + Send + Sync;

    const KIND: &'static str;                       // "file.template"
    const LOCKS: &'static [&'static str] = &[];      // "apt", "systemd", "dpkg"
    const REMOVAL_DEFAULT: RemovalPolicy = RemovalPolicy::Cleanup;   // every kind; authors opt out with `removal: leave`

    Secrets that cannot leak by accident

    Module authors and operators are trusted; the threat is accidents, not exfiltration. The goal is therefore structural: no code path formats, logs, serialises, diffs or displays a secret value, and the type system enforces it so a future contributor cannot leak one by mistake. Values exist in plaintext in exactly two places: inside the sealed Secret and inside a sink's write call, and every sink is greppable by its Witness.

    Rendering templates twice

    minijinja sees secrets as a custom object. In Mode::Redacted the object renders as «secret:nomad_server@3f9a»; in Mode::Real the renderer, which is itself a sink, reveals the value. The real render is returned as Sensitive<String>, which can only be written to disk or compared by digest. The redacted render is a plain Redacted<String> and becomes the shadow in state and the text shown in plans. Vars that are derived from secrets through templates (a URL with a token in it) inherit sensitivity: any template that touched a secret produces Sensitive, so the taint cannot be laundered through an intermediate var.

    What the operator sees

    - servers = ["«secret:nomad_server@3f9a»"] + servers = ["«secret:nomad_server@b21c»"] datacenter = "dc1" - node_class = "cloud" + node_class = "rpi"

    A rotated secret shows up as a fingerprint change on exactly the lines that use it; everything else in the diff is real. A file that contains a secret and has drifted on disk shows content changed outside Buckle (digest 9a1f… → 02c7…) rather than the hand edit, because reading the file back would mean handling plaintext outside a sink.

    Decision

    Secrets are resolved on the server and delivered per host, scoped to the modules the host selects. Agents hold no provider credentials. The server evaluates each host's module selection with the host's last reported facts, collects the secret references those modules use, resolves them and sends values inside the assignment over the Tailscale-encrypted stream. If an agent's local evaluation selects a module the server did not predict (facts changed), it asks for the missing names and the server checks the request against the revision before answering. In local mode (--source DIR) the agent resolves with its own providers.

    Decision · agreed

    Filters see secrets as filt-rs Secret values. Authors are trusted, so secrets.NAME == "x" and the other comparisons work in when expressions; filt-rs's secrecy feature renders the value as [REDACTED] on Display and Debug, so a selector that ends up in a log or a plan cannot carry it. secrets.NAME.present and secrets.NAME.fingerprint remain for the common "is it configured" and "did it rotate" cases. Filter error messages contain only filter text, never target values, so a bad expression is safe to show in the UI.

    Decision · agreed

    Providers for v2.0 are file and env; Nomad delivers the values. The server's Nomad job uses template stanzas over Nomad Variables (or Vault) to render one file per secret into the task's secrets directory, or env = true to inject them as environment variables; buckle.yaml references them with { file: /secrets/NAME } or { env: NAME }. Nomad re-renders on variable change and can signal the task, so rotation needs no Buckle-side integration. The file provider re-reads on each resolution (no caching), and values are trimmed of a single trailing newline. exec exists only behind an explicit allowlist in server config for local development, where op read is convenient; it is off by default and not part of the production story. Agents resolve nothing themselves in server mode.

    07

    Health checks

    Health is part of the module, not a separate monitoring system. Checks run when a rollout needs an answer (was this host healthy before we touched it, did the change leave it working, are the hosts we already changed still fine before we go further) and once alongside each periodic drift check, so the server always holds a recent baseline for the whole fleet. There is no separate health loop; uptime monitoring stays with Grey.

    1 · Baseline, before apply

    When a host's wave is due, the server sends RunHealth { scope: baseline } and the agent runs the checks of the modules it currently has applied. A failing baseline holds the host: the rollout does not touch an already-unhealthy host unless an operator forces it (force apply in the UI, audited). This separates "the change broke it" from "it was already broken".

    2 · Bake, after apply

    Once ApplyResult arrives, checks for every applied module run at their interval (default 30 s) for the phase's bake duration, then stop. A required check that stays failing for longer than settle (default 2 m, flap tolerance for services restarting mid-rollout) marks the host unhealthy, counts against max_failures, and pauses the rollout on breach; a check that recovers inside the settle window is recorded as a flap, not a failure. min_uptime on the systemd check catches crash loops inside the window.

    3 · Pre-phase, before advancing

    Before the next phase starts, the server sends RunHealth { scope: rollout } to every host this rollout has already updated and waits for all results. A regression anywhere pauses the rollout instead of advancing, so a slow-burning failure in the canary is caught before the fleet follows.

    4 · With each drift check

    Every drift.interval (default 15 m) the agent already re-plans its assigned revision; it now also runs the checks of its applied modules once and sends HealthReport { scope: drift } with the Drift message. This is the fleet's baseline health between rollouts: it drives the Overview roll-up, lets the UI show a host as unhealthy before anyone starts a rollout, and lets the controller pre-flag hosts that will be held at baseline. The pre-apply baseline check still runs fresh when the wave is due; the drift report is a recent reading, not a substitute.

    Session rules

    • Identity. On connect the server authenticates the peer by Tailscale whois when it can and by per-host token otherwise (both modes are always on; the decision card in 02 has the enrolment flow). Under whois the agent's claimed host_id must match the node name; under token auth the identity is the one bound to the token at enrolment. Labels come from two places: the agent reports its seed labels on connect, and operators manage server-side labels per host in the UI (stored in the database, never in server config). Server labels win on conflict, so an agent cannot promote itself out of the canary phase; the UI shows both sets and which one is effective.
    • Registration. A host the server has never seen is created on first Hello. With agents.registration: auto (the default under Tailscale auth) it is active immediately; with approve (recommended for token auth) it sits as pending, visible in the UI, excluded from rollouts until an admin approves it. Admins can also pause a host (kept in the fleet, excluded from rollouts and drift correction), resume it, or forget it (removes its record; a reconnecting agent registers afresh).
    • Stable revision cached locally. Welcome and Assign name the fleet's current stable revision; the agent keeps that revision's tree and its scoped secrets in the state directory (secrets at mode 0600, the same trust level as the files they render) so it can apply it with no server at all. See the local rollback rules in section 10.
    • Reconnect. Exponential backoff 1 s to 5 min with jitter (mail-backup's reconnect_min/max). On reconnect the agent sends Hello with its applied revision and the digest of its last plan, and the server resumes the host's rollout state from there rather than restarting it.
    • Assignment is not apply. Assign tells the agent what to fetch and plan. Only Apply with a matching plan digest mutates. If the agent's fresh plan digest differs from the approved one (the host changed in between), it refuses and reports stale plan; the server re-requests a plan and, if the phase requires approval, the UI shows the host as needing re-approval.
    • Backpressure. ApplyEvents are coalesced to at most 10 per second per host; the server stores the last event per step and the full stream goes to tracing.
    • Versioning. Hello carries the agent version; the server refuses agents older than its minimum and the UI shows version skew. protobuf field numbering keeps older servers working with newer agents within a major version.
    • Self-update. Buckle uses update-rs (git-tool's self-update crate, with its opentelemetry feature so the update is traced across the relaunch) for both buckle update on the command line and server-driven agent upgrades. When agents.desired_version is set, the server sends Upgrade to each host only while it is idle (no apply, bake or health run in progress), paced in the fleet's phase order with the phase's parallel limit but without plan approval; the agent downloads the GitHub release asset for its platform, verifies it, swaps the binary and exits so systemd (or launchd / SCM) restarts it, then reconnects with the new version in Hello. The server also upgrades itself the same way when an operator triggers it from the UI.
    • Local mode implements the same Transport trait with a filesystem watcher (notify): a directory change is an Assign of a synthetic revision, and apply is automatic.

    Server: revisions, Git, persistence

    The server is three loops sharing one SQLite database: a source watcher that turns commits into revisions, a rollout controller that moves hosts through phases, and the gRPC and HTTP fronts that feed them.

    Source watcher

    • A bare clone under data_dir/source.git managed with gix, fetched every poll (default 30 s) and immediately on POST /api/v1/webhooks/source (HMAC-verified, for a GitHub webhook over Tailscale Funnel or a Nomad-local forwarder).
    • Change detection compares the remote-tracking ref for the configured branch before and after the fetch (the audit of github-backup found that comparing HEAD misses remote-only updates).
    • Each new commit is loaded in memory, validated (schema, selectors parse, templates parse, module graph acyclic, every referenced secret declared) and stored as a Revision: commit id, author, message, timestamp, a content-addressed tarball of modules/ and vars/, and the validation report. Invalid commits are stored as rejected revisions so the UI can show the author what broke, and the fleet stays on the last valid one.
    • A path: source (local directory with a filesystem watcher) is supported for development and for a server fed by a CI job that already checked out the repo.

    Controller algorithm

    1. Freeze the target set. When the rollout starts, evaluate every phase selector against the current fleet (connected or not) and store the host-to-phase assignment with the rollout. A host matches the first phase whose selector is true and belongs to that stage only; it is never listed or re-applied in a later stage, even when that stage's selector would also match it. Hosts that miss their phase (offline during their wave, plan still pending, enrolled after the freeze, held at baseline and released later) are not lost: they move to the virtual stragglers stage, which runs after promotion (step 7).
    2. Plan everywhere first. Send Assign + RequestPlan to all targeted hosts up front, in parallel. Plans arrive over the following seconds; the UI groups them by digest. Disconnected hosts show as plan pending and do not block earlier phases.
    3. Gate. If the phase's approval policy requires it, wait for an approval that binds the phase's plan digests. A host whose plan changes after approval (stale) drops back to needs approval for that host only.
    4. Baseline. Before a host's wave starts, run the health checks of what it currently has applied. Unhealthy → the host is held per health.baseline (default: wait for an operator to force or skip it); the wave fills from the next host so one sick machine does not stall the phase.
    5. Waves. Apply to parallel hosts at a time. A host is done when ApplyResult is success and its bake window passed without a required check failing. Failures count against max_failures; on breach the phase enters Paused and nothing else is started.
    6. Bake. Each applied host repeats its checks for bake; the phase is baked when its last host is. Regression → Paused. Checks stop when the window closes.
    7. Pre-phase gate. Before advancing, re-run health on every host already updated by this rollout and wait for all results. Any regression → Paused, naming the host and check.
    8. Advance. Next phase. After the last phase bakes and its pre-advance check passes, the revision becomes stable: the revision new and reconnecting hosts converge to.
    9. Stragglers. Promotion opens a virtual final stage on the rollout holding every targeted host that was not updated during its phase, plus hosts enrolled since the freeze. Each is applied with the stable revision as it becomes available (baseline check, apply, bake), stragglers.parallel at a time, and its result is recorded on this rollout so the UI shows them in one place rather than scattered across host pages. A straggler failure marks that host needs attention and never un-promotes the revision or pauses anything else. The stage stays open until the next rollout is promoted, which carries any still-unfinished stragglers into its own stragglers stage. A rolled-back or aborted rollout never opens the stage.
    10. Paused offers four operator decisions, each audited:
      • Retry: re-plan and re-apply the failed host as it stands (the failed module is back on the stable version, the rest of the run is still pending); the same checks apply.
      • Continue: retry the failed host with the specific checks that failed (module + check names) waived for this rollout on this host, so the run proceeds past that module and finishes the remaining modules. The waiver is carried in the Apply message, shown on the host in the UI, and expires with the rollout; the checks still run and report, but no longer count. A task error (as opposed to a health failure) has nothing to waive, so continue is offered only for health failures.
      • Rollback: apply the previous stable revision to every host this rollout already updated, newest phase first.
      • Skip or abort: exclude the host with a reason and go on, or stop the rollout where it is with state recorded.
      A host that rolled a module back (section 04) arrives here with that module on the stable version and the rest of its plan unapplied; a host that rolled its whole revision back while disconnected arrives on the stable revision, with its evidence attached to the pause.
    Decision · agreed

    Rollback means "apply the previous stable revision", not "undo the diff". Because revisions are content-addressed and cached on agents, rolling back is the same operation as rolling forward, including removal cleanup for resources the new revision added. This is predictable and cheap. The limitation is honest: an irreversible task (a package upgrade with a schema migration) rolls back only as far as the task kind can take it, and the plan for the rollback shows exactly that.

    Decision · agreed

    Agents can roll themselves back when a change cuts them off from the server. Each agent keeps the current stable revision (tree and scoped secrets) in its state directory. After applying a new revision the agent watches two things for local_rollback.after (default 5 m): whether the server session it had before the apply comes back, and whether required health checks stay failing beyond settle. If it was connected before the apply, cannot re-establish a session within the window, and (with on_health) health is also failing, it applies the cached stable revision on its own, records a LocalRollback in state with the evidence, and reports it on reconnect. While the server is reachable the agent never decides alone: the server has fleet context and owns pause and rollback. The server treats a reported local rollback as that host failing its wave, which pauses the rollout. settle exists because a restarting service legitimately fails its check for a few seconds; only a failure that persists through the window counts, whether the agent or the server is judging.

    Edge cases handled: the server itself going down right after an apply looks like connectivity loss, which is why connectivity alone does not trigger a rollback by default (the on_health condition must also hold); a rollback that itself fails leaves the host in needs attention with both results recorded; an agent restart mid-window resumes the window from persisted state.

    Decision

    The controller is a persisted state machine. Every transition is a row update plus an audit event, so a server restart or a Nomad reschedule resumes mid-rollout. The in-memory part is only timers (bake deadlines) and the set of connected streams, both rebuilt from the database and the reconnecting agents.

    Your call

    Fleet size here is four hosts, so parallel: 1 everywhere is plausible and phases are mostly about canary-then-rest. The design still supports percentages and failure budgets because they cost little and matter if the fleet grows. Should automatic rollback (on_failure: rollback) be the default, or pause-and-wait as proposed? Pause is safer when the failure might be the health check rather than the change; rollback is better when nobody is watching.

    Web UI and authentication

    The UI follows automate and analytics exactly: a Yew application compiled to WebAssembly with Trunk, hand-written SCSS, a framework-free buckle-api DTO crate shared with the server, embedded with include_dir! and served with an SPA fallback.

    Decision · agreed

    OIDC uses the analytics variant: server-driven Authorization Code + PKCE, HttpOnly session and refresh cookies, double-submit CSRF. Tokens never reach the browser's JavaScript. Routes: /api/v1/auth/login, /callback, /refresh, /logout, /csrf; /api/v1/me returns 200 with the user or 204 when OIDC is not configured. Authorisation is two filt-rs ACLs over claims.*, client_ip, method and path: user_acl (may read) and admin_acl (may approve, pause, rollback, and manage hosts: labels, registration, pause, forget). Omitting oidc disables authentication for local development, with the ACLs still evaluated against request metadata.

    The automate variant (popup + bearer token in sessionStorage) avoids CSRF handling but keeps an ID token in the page. For a tool whose buttons mutate production hosts, cookies with CSRF is the safer default.

    Observability

    tracing-batteries everywhere, with one rule that v1 did not have: a rollout is one trace. The server starts it, every agent continues it, and the UI links to it.

    • rollout.run (server, root) → rollout.phase → rollout.host (one per host per wave) → the agent's agent.apply span, parented via traceparent in gRPC metadata → module.apply → task.plan / task.apply → handler.run → health.check.

    • buckle.apply.duration histogram by module and outcome

    Testing conventions

    • Unit tests inline (#[cfg(test)] mod tests), rstest cases, descriptive sentence names, as in the reference repos. A System fake makes task tests hermetic; a container suite exercises the real thing.
    • Secret leak tests are property-style: for every type that can hold a secret, format with Debug and Display, serialise with serde_json and serde_yaml, record on a tracing span with the Testing battery, and assert the plaintext never appears.
    • Protocol tests run server and agent in one process over a tonic channel; time is controlled with tokio::time::pause for bake and backoff.
    • Playwright e2e for the UI starts the real binary with OIDC disabled and with the wiremock IdP, following automate's e2e/ layout.
